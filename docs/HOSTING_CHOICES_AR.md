# أين تُنشر المنصة — موازنة بالتكلفة والجهد

كُتب في 2026-07-25 لأن صاحب المشروع لا خادم لديه بعد. الغرض قرارٌ مبنيّ
على ما تحتاجه هذه المنصة تحديدًا، لا مسحٌ عام لمزوّدي الاستضافة.

## ما تحتاجه هذه المنصة بالضبط

| المطلب | لماذا |
| --- | --- |
| **Postgres** بحجم دائم | ~150 م.ب بعد الاستيراد (6236 آية + 128,219 مقطعًا + 49,968 موضع جذر) |
| **ذاكرة ≥ 1 جيجابايت** | الاستيراد يحمّل حزمة 1.7 م.ب مضغوطة ويعالجها دفعة |
| **حجم دائم للنسخ** | سجل التدقيق ملحق-فقط ولا يُعاد بناؤه |
| **دور قاعدة مالك + دور تطبيق** | الفصل مبنيٌّ في التركيب ومختبَر |
| **تنفيذ أوامر لمرة واحدة** | الهجرات والبذر خطوتان مستقلتان بدور المالك |
| **TLS على نطاق** | عامل الخدمة لا يعمل بلا HTTPS، فلا PWA بدونه |

> **ما لا تحتاجه:** لا CDN، ولا توسّع أفقي، ولا طوابير. المنصة بحثية
> القراءة فيها أضعاف الكتابة، وكل بياناتها تسع في ذاكرة خادم صغير.

## الخيارات الثلاثة

### ١) خادم VPS بدوكر — **الأوفق لهذه المنصة**

كل شيء جاهز لهذا الطريق: `docker-compose.prod.yml` و`ops/Caddyfile`
و`ops/backup.sh` وسكربتات تهيئة الأدوار.

| | |
| --- | --- |
| **التكلفة** | 4–6 دولار شهريًا (Hetzner CX22، أو Contabo، أو DigitalOcean) |
| **ما تملكه** | الخادم كاملًا: القاعدة والنسخ والسجلات وTLS |
| **جهدك** | إنشاء الخادم، ونطاق (~10 دولار سنويًا)، وتنفيذ ٧ أوامر |
| **صيانتك** | تحديثات النظام، ومراقبة المساحة، ونقل النسخ خارج الخادم |

**لماذا هو الأوفق هنا:** شرط ليدز **غير التجاري** يجعل المنصة مشروعًا
بحثيًا لا منتجًا مدرًّا، فالتكلفة الثابتة المنخفضة أهم من التوسّع. وقيد
«لا يُنشر مخرَج آلي بوصفه معتمدًا» يعني أن الاستيراد والتفعيل عمليات
إدارية مقصودة تحتاج وصولًا مباشرًا إلى الحاوية — وهو أيسر ما يكون على
VPS.

### ٢) منصة سحابية مُدارة (Railway / Render / Fly.io)

| | |
| --- | --- |
| **التكلفة** | 10–25 دولار شهريًا (خدمتان + Postgres مُدار) |
| **المكسب** | لا صيانة نظام، وTLS ونسخ القاعدة تلقائيان |
| **الكلفة الحقيقية** | تُهجر معظم البنية الجاهزة: Caddy وخدمة النسخ وسكربتات الأدوار |

**تنبيهان قبل اختياره:**

1. **الأصل الواحد ينكسر.** الواجهة والـAPI يصيران نطاقين، فيلزم ضبط
   `ALLOWED_ORIGINS` بدقة، **ويفقد عامل الخدمة قدرته على تخزين ردود
   الـAPI** لأنها تصير من أصل آخر.
2. **دور التطبيق غير المميز** لا تدعمه كل المنصات؛ بعضها يعطيك دورًا
   واحدًا مالكًا — فتسقط طبقة الحماية الثالثة على سجل التدقيق.

### ٣) لا تنشر بعد — شغّلها محليًا

جائز تمامًا، والمنصة تعمل كاملة على جهازك بأمر واحد:

```bash
docker compose up -d
```

وينفع لمراجعة العمل العلمي قبل فتحه للناس. لكن **لا PWA بلا HTTPS**،
فالتثبيت على الهاتف يحتاج نشرًا فعليًا.

## خطوات النشر على VPS — ٧ أوامر

بعد إنشاء الخادم وتوجيه النطاق إليه:

```bash
# 1) نقل المشروع (أو git clone بعد الدفع إلى مستودع خاص)
scp -r qsp/ root@SERVER:/srv/qsp

# 2) الأسرار
cd /srv/qsp && cp .env.production.example .env
#    املأ كل قيمة، وولّد السرّ بـ: openssl rand -base64 48

# 3) القاعدة أولًا (تُنشئ دور التطبيق عند أول تهيئة)
docker compose -f docker-compose.prod.yml up -d postgres

# 4) الهجرات بدور المالك — خطوة مستقلة عمدًا
docker compose -f docker-compose.prod.yml run --rm \
  -e DATABASE_URL="postgresql+asyncpg://$POSTGRES_OWNER:$POSTGRES_OWNER_PASSWORD@postgres:5432/$POSTGRES_DB" \
  api alembic upgrade head

# 5) تحصين سجل التدقيق (بعد الهجرات، لا قبلها)
docker compose -f docker-compose.prod.yml exec -T postgres \
  psql -U "$POSTGRES_OWNER" -d "$POSTGRES_DB" \
  -v app_role="$POSTGRES_APP_USER" < ops/sql/audit-hardening.sql

# 6) البذر ثم خط المعالجة
docker compose -f docker-compose.prod.yml run --rm api python -m app.cli seed
docker compose -f docker-compose.prod.yml run --rm api python -m app.cli pipeline

# 7) الإقلاع الكامل — ومعه بصمة البناء
#    بدونها لا يُبطَل مخزن عامل الخدمة، فيبقى الزوار على نسخة قديمة
export BUILD_ID=$(git rev-parse --short HEAD)
docker compose -f docker-compose.prod.yml up -d --build
```

ثم **نفّذ قائمة التحقق في `DEPLOYMENT_AR.md` §7 قبل أن تعلن الموقع**،
وجرّب استرجاع نسخة احتياطية مرة واحدة على الأقل قبل فتح التسجيل.

## ما يبقى بعد النشر

- نقل النسخ الاحتياطية **خارج الخادم** (حجم `backup_data` يذهب معه).
- الدفع إلى مستودع خاص على GitHub لتعمل `.github/workflows/ci.yml`.
- مراقبة: تنبيه عند امتلاء القرص وعند فشل خدمة النسخ.
