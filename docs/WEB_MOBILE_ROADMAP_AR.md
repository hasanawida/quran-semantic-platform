# خارطة طريق الموقع وتطبيق الهاتف

**الهدف:** إيصال المنصة للمستخدمين موقعًا ويب وتطبيق هاتف (Android وiOS) دون المساس بالسلامة العلمية، وبفريق صغير.

---

## القرار المعماري الموصى به

**API أولًا، الموقع أولًا زمنيًا، ثم تطبيق Expo/React Native يشارك العقد نفسه.**

المسوغات:

1. **الفريق صغير والمخاطرة الدينية عالية** — إطلاق قناة واحدة (الويب) بمحتوى معتمد أهم من قناتين ناقصتين.
2. **الويب الحالي Next.js/React** — اختيار React Native/Expo لاحقًا يتيح مشاركة المعرفة والأنواع (types) وعميل API، بخلاف Flutter الذي يفتح مسارًا تقنيًا ثانيًا كاملًا.
3. **تطبيق قرآن بلا اتصال ليس ترفًا** — يحتاج تصميم تزامن قائم على إصدارات البيانات (`data_releases` موجودة أصلًا في تصميم الوثيقة) وبصمات التحقق، وهذا يبنى في الـ API أولًا.
4. **PWA جسر مبكر** — الأساس وضع الآن (manifest + أيقونة)؛ إضافة service worker لاحقًا تعطي تجربة هاتف قابلة للتثبيت قبل اكتمال التطبيق الأصيل.

## المراحل

### المرحلة 0 — أساس مشترك (أسبوعان، تبدأ فورًا)

- [ ] اعتماد **Alembic** للهجرات (شرط لكل ما بعده).
- [ ] تثبيت **عقد OpenAPI** كملف مُصدَّر في `openapi/` يتحدث تلقائيًا في CI، مع فحص كسر التوافق (oasdiff).
- [ ] **مصادقة جاهزة للهاتف من اليوم الأول:** JWT قصير العمر + Refresh Token دوّار (لا كوكي جلسة فقط) — سواء عبر Supabase Auth كما تقترح الوثيقة أو تنفيذ ذاتي.
- [ ] monorepo فعلي بـ **npm workspaces**: `packages/types` (يولَّد من OpenAPI)، لاحقًا `packages/api-client`.
- [ ] إضافة rate limiting (Redis موجود بلا استخدام) وlogging منظم وSentry.

### المرحلة 1 — إطلاق الموقع بمحتوى معتمد (4–8 أسابيع)

- [ ] خط استيراد النص القرآني الموثق (المصدر المرشح: Tanzil أو QUL — **يتحقق من الترخيص والشروط قبل الاستخدام**، وتوثق النسخة والرواية والبصمة).
- [ ] توليد `plain_search_text` عبر جدول قواعد رسم عثماني → إملائي (الألف الخنجرية، الألف المحذوفة، الألف الصامتة…) مبني على سياسة التطبيع المصلحة في `app/utils/arabic.py`.
- [ ] صفحات: السورة، الآية، الجذر ومواضعه — **بروابط عميقة** (`/surah/2/255`, `/root/سءل`) فهي شرط لمشاركة المحتوى ولتطبيق الهاتف لاحقًا.
- [ ] متحكم حجم النص القرآني (المتغير `--quran-font-size` جاهز).
- [ ] المصدر الصرفي الأول والمقارنة (سبرنتات الوثيقة 5–7 مختصرة).
- [ ] Staging + نسخ احتياطي مجرب + مراقبة — ثم **إطلاق تجريبي مغلق**.

### المرحلة 2 — PWA كامل (أسبوعان، بالتوازي مع نهاية المرحلة 1)

- [ ] Service worker بتخزين النص القرآني المعتمد للقراءة دون اتصال (cache مفتاحه إصدار البيانات + البصمة).
- [ ] شاشة «الإصدار المخزن لديك: 2026.1 — التحقق من البصمة ✓» لبناء الثقة.

### المرحلة 3 — تطبيق الهاتف Expo/React Native (8–12 أسبوعًا)

- [ ] `apps/mobile` بـ Expo، يستهلك `packages/api-client` المولد من العقد.
- [ ] **قاعدة بيانات محلية (SQLite)** تنزَّل حزمة إصدار البيانات كاملة (نص + جذور معتمدة) موقعة بالبصمات؛ البحث محليًا دون اتصال.
- [ ] **إعادة تنفيذ التطبيع العربي في TypeScript داخل `packages/arabic-utils` مع نفس الاختبارات الذهبية حرفيًا** (سياسة الهمزات الموحدة) — الاختبارات المشتركة هي صمام الأمان ضد انحراف المنطقين.
- [ ] روابط عميقة (universal links) تطابق مسارات الويب.
- [ ] إشعارات لاحقًا (تقارير جديدة منشورة) عبر apps/worker.
- [ ] النشر: TestFlight / Internal testing ثم المتاجر، مع مراعاة سياسات المحتوى الديني في المتجرين (تصنيف المحتوى، وضوح المصدر).

### المرحلة 4 — ما بعد الإطلاق

- مشاريع الباحثين والمراجعة والتقارير (سبرنتات 8–12) تفعَّل في الويب أولًا؛ الهاتف يبقى قناة قراءة وبحث حتى تنضج.
- الذكاء الاصطناعي وفق ضوابط الوثيقة (قسم 17) — آخر ما يبنى، ولا يتاح للعامة في النسخة الأولى.

## قرارات تقنية محددة

| القرار | الاختيار | البديل المرفوض ولماذا |
|---|---|---|
| تقنية الهاتف | Expo / React Native | Flutter: مسار تقني ثانٍ كامل لفريق صغير؛ Capacitor: تجربة أدنى لتطبيق قراءة طويلة |
| مشاركة الكود | OpenAPI → types + client مولدان | نسخ يدوي: انحراف حتمي |
| Offline | حزم إصدارات موقعة ببصمات + SQLite | مزامنة لحظية: تعقيد بلا حاجة — النص القرآني لا يتغير إلا بإصدار |
| التطبيع في العميل | إعادة تنفيذ TS باختبارات ذهبية مشتركة | WASM من بايثون: تعقيد بناء غير مبرر لدالة صغيرة |
| المصادقة | JWT + Refresh (أو Supabase Auth) | كوكي جلسة فقط: يعقد الهاتف |

## تنبيهات ترخيص (يجب حسمها قبل المرحلة 1)

- **نص المصحف:** Tanzil وQUL لكل منهما شروط إسناد وإعادة توزيع — تراجع وتوثق في سجل المصادر قبل الاستيراد.
- **الخطوط:** Amiri وNoto مرخصة OFL — سليمة للاستخدام والتضمين.
- **المعاجم والتفاسير:** لا يدخل أي مصدر دون سجل ترخيص (متطلب الوثيقة 12.1) — القيد يطبق تقنيًا بحقل `license_status` قبل تفعيل أي مصدر.
